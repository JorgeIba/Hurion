# ADR 0003: Mentor Problem Management through Slash Commands, Batches, and an API

* **Status**: Decision accepted on 2026-09-30; models and mappings implemented, runtime work pending
* **Date**: 2026-09-29
* **Updated**: 2026-10-03; restored planning alongside the reviewed models and mappings
* **Implementation plan**: [Slash problem management](../plans/slash-problem-management.md)

## 1. Context

Mentors manage problems through positional Discord commands. Adding a problem requires a class, URL, difficulty placeholder, topic placeholder, and name. Updating one field requires resending all fields. This makes routine corrections cumbersome and preparing a class repetitive.

The existing problem service already supports creation, retrieval, update, and removal. Permissions are checked in mentor controllers, while service methods accept no acting user. The message handler uses `strings.Fields` on the entire message, so multiple command lines currently become one command. The JSONL script runner provides developer automation but requires access to the bot runtime.

The scoreboard frontend reads exported JSON and the web server serves static content. It is not a problem-management API. Production currently follows [ADR 0002](0002-container-delivery-and-cicd-pipeline.md), including no public inbound access. Slash commands can arrive over the existing Discord gateway connection; a remotely accessible API needs an explicit hosting decision.

Repository evidence: [command definitions](../../app/bot/commands.go), [message routing](../../app/bot/bot.go), [mentor controllers](../../app/controllers/mentor/mentor.go), [problem services](../../app/services/problem_service.go), [script runner](../SCRIPT_RUNNER.md), and [web server](../../web/server.go).

## 2. Decision

Introduce three interfaces in phases, sharing typed problem operations and authorization:

1. **Slash commands and forms** for interactive mentor editing.
2. **Explicit text batches** for preparing many changes, including files generated by an agent.
3. **An authenticated HTTP API** for integrations and direct automation.

An MCP adapter can be added if mentors need an AI client to invoke these operations. It is optional and consumes the same application operations; it does not introduce another database writer or a separate permission policy.

The first implementation targets slash problem management. Batch execution, API access, token issuance, and MCP are later phases with separate implementation review. This ADR records their contracts so the slash work leaves a clear extension path.

### Shared application boundary

Transport adapters turn Discord options, form fields, command lines, or JSON into typed requests. A small application-level problem manager receives the verified actor's user and guild IDs, checks current permissions, validates input, and calls existing domain services. Discord objects and HTTP authentication details remain in their transport/provider layers.

Build only the operations needed by the active phase. Do not introduce a general command framework or refactor unrelated student, score, class, or confirmation flows. Prefix problem-management controllers should delegate to the same authorization and validation path when that path is introduced.

### Phase 1: Slash commands

The refined implementation proposal targets `/problem add` and `/problem edit`, with problem autocomplete, forms containing existing values, and private results. Defer `/problem list` in phase 1 because `!list` and the deployed web Problems tab already provide browsing. Editing preserves problem IDs and solved records. Initial scope covers additions and edits including class moves, approved during review on 2026-10-01; destructive slash operations require later design.

For addition, the class is always a required form field. Prefill it using the current channel's classroom mapping when available; an unlinked channel requires manual class entry. The add command does not require a redundant class option. This form-entry decision was agreed on 2026-09-30. **Revised on 2026-10-01:** editing prefills a required Class field from the problem's existing class. A mentor may change it to correct a problem added to the wrong class. Validate and resolve the submitted destination class before saving the same problem ID; correction forms retain the proposed class code. During step-1 review on 2026-09-30, difficulty was simplified to a prefilled optional text field; blank means unspecified. Defer the dropdown independently of the layout choice. The user approved pinning an upstream DiscordGo commit for native Label wrappers and submission decoding. The detailed plan records the exact SDK version/commit, the unreleased-dependency tradeoff, and the live compatibility gate before rollout.

Runtime checks remain authoritative even when Discord command visibility is configured. The approved management policy permits the configured mentor or admin role; this policy also allows admin-only users to use the existing add/update prefix commands through the shared manager. Current controllers check only the mentor role. Class access roles describe student access, not mentor assignments; do not infer per-class mentor restrictions from them.

Receive interactions through the Discord gateway. Initial acknowledgements have a deadline and cannot depend on an ordinary outbound queue. Keep response delivery in the dispatcher/provider transport boundary, with a dedicated immediate interaction response path. Existing queued channel messages continue through the dispatcher.

Use Otter v2 for temporary in-process editor storage, selected by the user on 2026-09-30. A small editor-specific wrapper owns user/guild binding, atomic submission claims, fixed draft deadlines, and capacity admission. New requests are rejected when full rather than evicting active editors. Claimed saves remain protected until completion. Draft persistence and shared session infrastructure are outside phase 1.

The detailed plan defines command registration, form sessions, response timing, concurrent-edit behavior, SDK compatibility, tests, and rollout, in independently reviewable increments. The current delivery contains models, mappings, and planning; the next SDK/basic-modal proof must be discussed before coding. Its approved stricter field validation intentionally changes prefix add/update acceptance and includes a legacy repair policy; each implementation increment awaits its own review. On 2026-09-30 the user accepted last successful write wins for editable fields in phase 1: submitting an older form may overwrite another mentor's newer changes, including unchanged prefilled fields. With class editing approved on 2026-10-01, this includes class membership; an older form can move a problem back after another mentor moved it. Expected-snapshot conflict detection and its reload workflow are deferred. Duplicate execution prevention, current permission checks, and preservation of problem identity and solved records remain required. Submitted destination classes must exist; current class membership may change through the form.

#### Modal ownership and adapters

**Current architecture, reviewed on 2026-10-03:** `CreateProblemModal` and `EditProblemModal` live in `app/presentation/discord`, sharing raw `ProblemModalFields`. Both contain an editable class code; the future create flow defaults it from the channel and edit from the selected problem. Use Create consistently in internal creation models and mappings; the existing public `!add_problem` spelling remains a separate interface contract.

Keep both directions of params-to-modal mapping together in `app/presentation/discord/problem_adapters.go`. Presentation may import application model types; services must not import Discord presentation types. The service-only `MapProblemToUpdateProblemParams` stays in `app/services/adapters.go`. Public mappings use `MapSourceToDestination`; private conversion helpers use `mapSourceToDestination`. Controllers coordinate actor checks, sessions, class lookups, response delivery, and application calls.

The implemented prefill path is `Problem -> UpdateProblemParams -> EditProblemModal`. Update params carry ProblemID and numeric ClassID; create params use ClassCode. The edit prefill mapper receives the separately resolved class code. The reverse edit mapper receives the session-owned target ID and the class ID resolved from the submitted code; it ignores display metadata. These mappings perform no lookup, authorization, validation, or write. The existing update service still accepts a separate problem ID and stored `Problem`; consuming `UpdateProblemParams` at that boundary is later work.

Preserve saved nil values and explicit raw text during preparation. For display, a missing difficulty uses the existing Not specified label and a missing topic becomes blank. Submission mappings convert blank optional text and unspecified difficulty to nil; other text remains raw for later application validation. A params struct is not evidence that validation has passed. This mapping policy is separate from the future shared business rules.

DiscordGo will decode JSON/component types. Future presentation parsing checks the expected fields, duplicates, component types, and reviewed transport bounds. Shared application validation checks problem rules before saving. Field length limits are still to be agreed and centralized; do not adopt Discord's maximum input size as the class-code domain limit. Builders, submission parsers, and runtime handlers are not implemented in this delivery.

**Problem ID display:** `EditProblemModal.ProblemID` is metadata for a future title such as `Edit problem #42`. The intended five inputs are Class, Name, URL, Difficulty, and Topic. Saving uses the owned session's target ID, and the controller restores display metadata when reopening a correction form. No editable ID field is proposed.

#### DiscordGo version and upgrade follow-up

**Planned dependency change, approved on 2026-09-30:** upgrade from DiscordGo `v0.28.1` to `v0.29.1-0.20260214123928-f43dd94faaac`, pinned to upstream commit `f43dd94faaacd5b163e9e783f14b5bd8be639fc9`. Its [native component implementation](https://github.com/bwmarrin/discordgo/blob/f43dd94faaacd5b163e9e783f14b5bd8be639fc9/components.go) supports both creating Label wrappers and decoding their submitted TextInput children. Discord [recommends Labels and deprecates the previous Action Row/TextInput layout](https://docs.discord.com/developers/components/reference#text-input). The pin lets us adopt that layout without a custom encoder or SDK fork. Difficulty remains prefilled text; dropdown support is a separate deferred decision.

The current branch still uses DiscordGo `v0.28.1`. The planned pin is an upstream commit rather than a tagged release. Before implementing the dependency change, check whether a compatible tag is available and review any change to the selected version. When implemented, record the selected version in `go.mod` and checksums in `go.sum`; run repository tests and compilation to verify compatibility with the bot. Independent protocol fixtures verify native encoding and decoding, including explicit `Required=false` for optional fields. Live Discord acceptance and desktop/mobile behavior still require the test-guild check before rollout.

**Upgrade follow-up:** when a tagged DiscordGo release supports the same Label/TextInput contract, replace the pseudo-version in a separate reviewed dependency change. Confirm native submission decoding and explicit optional flags, update `go.mod`/`go.sum`, run the form contract tests, full `make test`, and bot build, and verify the forms in the test guild before deploying the upgrade. Update this ADR and the implementation plan with the chosen tag and verification results. Keep the existing form behavior and deferred dropdown scope; a new release does not by itself authorize deployment or publishing.

### Phase 2: Explicit command batches

Accept a `.txt` attachment or multiline input through an explicit batch command. Start with problem addition and update operations. An agent converts a mentor's natural-language request into the supported command format; the bot parses that format deterministically.

Parse one operation per line, retain original line numbers, and support quoted fields for multiword topics when defining the batch grammar. Validate the whole proposal before showing a preview. Bind approval to the submitting actor and guild, expire it, and recheck authorization at execution.

Execute sequentially and stop at the first runtime failure. Return successful problem IDs, the failed line, and the unexecuted lines. Earlier successful changes remain applied. The initial contract does not promise an all-or-nothing transaction or automatic replay; resume the failed and unexecuted work explicitly. Durable progress and retry recovery need their own design before those capabilities are advertised.

Send one result summary per batch. Keep the existing developer script runner distinct from this mentor-facing batch workflow.

### Phase 3: Authenticated API

Expose structured problem resources and batch requests, such as `GET /api/v1/problems`, `POST /api/v1/problems`, and `PATCH /api/v1/problems/{id}`. Avoid a general endpoint that accepts arbitrary Discord command strings.

Use personal, random, revocable access tokens issued through a verified Discord identity. Store token hashes, associate each token with its owner and guild, and restrict its allowed operations. A token's permissions cannot exceed its owner's current role. Resolve the acting identity from the token, rather than an issuer supplied in JSON. Require HTTPS and check permissions for each operation.

Define partial update semantics explicitly: omitted fields remain unchanged; explicit null clears only fields that permit clearing. For retryable creation and batch writes, commit the mutation and its saved idempotency result together, and serialize requests using the same key. Saving a progress marker separately does not prevent duplicates after a crash.

Return structured HTTP results to the caller. Optional Discord DMs provide receipts, with one summary for a batch. Report notification delivery separately from mutation success; failed DM delivery does not undo a completed write. Asynchronous or approval-dependent operations need durable status that the caller can query.

Host the API application logic in the bot process and reuse its services and database connection configuration. Before exposing it remotely, resolve how authenticated clients reach it under ADR 0002's current network constraints. Public ingress, a private network, or an outbound tunnel must be evaluated in that phase; this ADR does not authorize opening production ports.

## 3. Alternatives and Tradeoffs

| Approach | Benefit | Cost or limitation |
| --- | --- | --- |
| Improve prefix commands only | Small change; existing entrypoint | Positional syntax remains difficult to discover and edit |
| Slash forms first | Native Discord workflow; structured input | Interaction response timing, registration, and session handling |
| Text batches | Agent-generated files without production credentials | Grammar, preview, partial failure, and resume behavior |
| API first | Flexible integrations and automation | Tokens, hosting, authorization, retries, and delivery status |
| MCP first | Direct use from compatible AI clients | Client setup and protocol/authentication work before a stable operation contract |
| Web administration UI | Strong option for extensive browsing and bulk editing | Authenticated write backend plus a separate frontend workflow |

Choose slash forms first because mentors already work in Discord. Add batches when the interactive operation path is established. Introduce the API when direct integrations justify its operational work. Evaluate MCP and a web editor against actual mentor demand.

## 4. Review and Rollout

1. Review this ADR and the linked slash implementation plan.
2. Approve the phase-1 scope, role policy, response flow, and SDK strategy before code implementation.
3. Implement and validate slash commands in an isolated test guild, then register them explicitly for production after rollout approval.
4. Review the batch grammar and execution contract before phase 2.
5. Review API hosting, token lifecycle, and retry guarantees before phase 3.

Existing prefix commands remain available during rollout. Each transport reports the same problem operation outcomes. Scope and rollout approval are separate from merely creating planning documents.
